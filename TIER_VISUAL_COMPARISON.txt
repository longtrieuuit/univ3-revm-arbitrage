OPTION A: Single Binary with Config File (BAD)
──────────────────────────────────────────────────────────────────────────────

$ cargo run -- --strategy=rpc
$ cargo run -- --strategy=revm
$ cargo run -- --strategy=mock


Problems:
❌ 1. Single binary loads ALL dependencies
   ├─ eth_call doesn't need REVM
   ├─ But has to load REVM anyway
   └─ = Larger binary, slower startup

❌ 2. Complex initialization code
   ├─ If-else-if for each strategy
   ├─ Hard to follow logic
   └─ Easy to introduce bugs

❌ 3. No clear separation
   ├─ Changes to TIER 1 might affect TIER 2
   └─ Harder to test & debug

❌ 4. Educational value lost
   ├─ User doesn't see "one thing per binary"
   ├─ Confusion about what each strategy does
   └─ Harder to learn

❌ 5. Binary bloat
   ├─ Includes code for all 3 strategies
   ├─ Larger on disk & memory
   └─ Slower compilation


OPTION B: 8 Separate Binaries (GOOD) ✅
──────────────────────────────────────────────────────────────────────────────

$ cargo run --bin eth_call_one --release
$ cargo run --bin eth_call --release
$ cargo run --bin revm_cached --release
$ cargo run --bin revm_arbitrage --release


Advantages:
✅ 1. Each binary = lean & focused
   ├─ eth_call doesn't load REVM
   ├─ revm doesn't load Anvil
   └─ = Smaller, faster binaries

✅ 2. Clear initialization
   ├─ No if-else confusion
   ├─ Easy to understand each
   └─ Obvious what each does

✅ 3. Strong separation
   ├─ Changes to eth_call.rs
   ├─ Don't affect revm.rs
   └─ Easier testing & debugging

✅ 4. Educational clarity
   ├─ Binary name = purpose
   ├─ "eth_call" = RPC calls
   ├─ "revm_cached" = REVM optimization
   └─ Easy to learn progression

✅ 5. Accurate benchmarking
   ├─ eth_call vs revm_cached
   ├─ True apples-to-apples comparison
   └─ No overhead from other strategies


DECISION: Use separate binaries! ✅
